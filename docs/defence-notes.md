# EchoClass engineering defence notes

These notes describe the `3.0.0-beta.3` Milestone 2A.2 provenance-closure implementation. Future capabilities are explicitly separated at the end.

## Repository Pattern

**What it is**

An interface between application workflows and persistence operations, with concrete storage kept outside the application layer.

**Why EchoClass uses it**

It prevents HTTP/services from depending on SQLite or JSON details and makes authorization workflows testable with in-memory repositories.

**Where it is implemented**

Ports are in `src/domain/repositories.ts`; the current adapter is `src/infrastructure/repositories/storage-adapter.ts`; composition is in `src/server.ts`.

**How it is tested**

Service tests inject memory repositories, integration tests exercise the real adapter, and the architecture test rejects forbidden dependency edges.

**Limitations**

The underlying storage engine remains JavaScript, and the JSON fallback is not equivalent to SQLite operationally.

**Likely interview questions**

- Why use focused repositories instead of one generic CRUD interface?
- How would a PostgreSQL adapter change the composition root and tests?

## Service Layer

**What it is**

Application classes that own complete use cases between transport parsing and repository/provider ports.

**Why EchoClass uses it**

Authorization, trusted identity, deterministic diagnostics, auditing, and error semantics need one consistent boundary outside route handlers.

**Where it is implemented**

`src/application/*-service.ts`, including authentication, experiments, reviews, administration, practice, class summary, operations, and AI.

**How it is tested**

Unit tests call services with test doubles; HTTP integration tests verify the same behavior through routes.

**Limitations**

Some services coordinate current legacy data shapes, and there is no transaction-oriented unit-of-work abstraction.

**Likely interview questions**

- Which rules belong in a service versus the domain or HTTP parser?
- How do you prevent services from becoming new monoliths?

## Dependency Direction

**What it is**

Domain code is inward and independent; application code depends on domain/ports; infrastructure implements ports; HTTP invokes application services.

**Why EchoClass uses it**

It keeps transport, database, and provider details from controlling scientific and authorization rules.

**Where it is implemented**

The directory layout under `src/domain`, `src/application`, `src/http`, and `src/infrastructure`, wired only by `src/server.ts`.

**How it is tested**

`tests/architecture-boundaries.test.ts` scans imports and specific route responsibilities; CI invokes the built test directly.

**Limitations**

The rule is a project-specific source scan, not a complete TypeScript compiler plugin, and the legacy view adapter remains allowed at the HTTP edge.

**Likely interview questions**

- Why is the composition root exempt from the normal edge rules?
- What invalid dependency did the architecture gate catch during remediation?

## RBAC and Resource-Level Authorization

**What it is**

RBAC decides which roles may invoke a capability; resource-level checks also constrain records and class data to the authenticated actor's scope.

**Why EchoClass uses it**

Showing or hiding UI controls cannot stop a student or teacher from calling an endpoint for another class.

**Where it is implemented**

Policies are in `src/domain/authorization.ts`; services apply role and class checks before repository operations.

**How it is tested**

Unit policy tests and integration workflows verify student/teacher cross-class denial and administrator-only operational metrics.

**Limitations**

The current user/class model is not a normalized enrollment or multi-school permission system.

**Likely interview questions**

- What is the difference between RBAC and object-level authorization?
- Where must a class-scope check run to avoid an insecure direct object reference?

## Canonical Server IDs

**What it is**

Database primary IDs are generated by the server and are independent of any browser submission identifier.

**Why EchoClass uses it**

It prevents client-controlled collision and replacement of existing records.

**Where it is implemented**

`ExperimentService` receives the ID generator; storage uses insert-only SQL; the browser stores returned mappings.

**How it is tested**

Collision regression tests prove the original record remains unchanged and the new submission receives another ID.

**Limitations**

IDs provide identity, not authorization; every read/update still needs actor and class checks.

**Likely interview questions**

- Why is rejecting collisions weaker than never trusting client primary IDs?
- How are IDs generated deterministically in tests?

## Idempotency

**What it is**

Repeated offline submissions with the same client submission token return the existing canonical mapping instead of creating duplicates.

**Why EchoClass uses it**

Browsers may retry synchronization after an uncertain connection result.

**Where it is implemented**

The strict creation parser accepts `client_submission_id`; `ExperimentService` scopes lookup metadata by actor and class; `public/client.js` stores mappings.

**How it is tested**

Integration tests repeat a submission and then reuse the same token under a second actor to prove both replay handling and scope isolation.

**Trade-offs**

The client must retain the canonical mapping, while the database pays for a partial unique index and conflict handling on writes.

**Limitations**

The SQLite constraint protects authoritative persistence, but explicit JSON compatibility mode cannot provide equivalent concurrent uniqueness.

**Likely interview questions**

- Why can an idempotency key not double as the primary key?
- What database constraint would be needed for concurrent writers?

## Request IDs

**What it is**

A server-generated identifier attached to each request, safe error envelope, response header, and metadata log event.

**Why EchoClass uses it**

It correlates a user-visible failure with operational logs without returning stack traces or SQL details.

**Where it is implemented**

`src/http/router.ts`, `src/http/request.ts`, `src/http/response.ts`, and structured logger calls.

**How it is tested**

HTTP tests verify structured responses and security/runtime checks exercise the real built request/response modules.

**Limitations**

There is no distributed trace backend, and request IDs alone do not provide end-to-end tracing across external services.

**Likely interview questions**

- Should a server trust an inbound request ID?
- How do request IDs help without leaking sensitive context?

## Structured Errors

**What it is**

Stable application codes and status mappings with safe messages, optional validation findings, and request IDs.

**Why EchoClass uses it**

Clients need predictable failure handling while SQLite errors, stack traces, paths, and provider internals remain private.

**Where it is implemented**

`src/application/errors.ts` and the HTTP error mapper/response helpers.

**How it is tested**

Tests cover validation findings, authentication/authorization, rate limiting, not-found behavior, and duplicate persistence mapped to `CONFLICT` without SQLite details.

**Limitations**

Messages are currently application-local strings rather than a formal localization catalogue.

**Likely interview questions**

- Why separate a stable error code from a human-readable message?
- How are unexpected exceptions prevented from exposing infrastructure details?

## Demo/Production Data Isolation

**What it is**

Public pages use immutable anonymous demo records, and fixed demo users/records seed only under an explicit opt-in flag.

**Why EchoClass uses it**

Public analytics must not read classroom repositories, and known demo credentials must not silently appear in real-data deployments.

**Where it is implemented**

`src/shared/demo-records.ts`, public page routes, storage seeding, `src/config/env.ts`, and `.env.example`.

**How it is tested**

Integration tests insert a private record and prove public theme output is unchanged; baseline tests verify the flag and ignored runtime files.

**Limitations**

Owners must manually audit older deployment directories; the flag does not delete legacy demo accounts.

**Likely interview questions**

- Why is anonymous demo data still kept separate from repository queries?
- What could go wrong if demo seeding were the default?

## Automated Testing

**What it is**

Layered checks for pure rules, application services, HTTP/storage workflows, runtime security, smoke behavior, formatting, typing, and architecture.

**Why EchoClass uses it**

Trust boundaries need both focused regressions and end-to-end evidence through the actual runtime modules.

**Where it is implemented**

`tests/*.test.*`, `tests/integration`, `scripts/smoke-test.mjs`, `scripts/security-check.mjs`, and npm scripts.

**How it is tested**

The verification gate runs the test tools themselves and records exact pass counts; disposable data directories avoid private/runtime fixtures.

**Limitations**

No coverage percentage, performance benchmark, scientific validation study, or cross-platform browser suite is claimed.

**Likely interview questions**

- Why are collision and cross-class tests integration tests as well as unit tests?
- What does a passing smoke test prove—and what does it not prove?

## Continuous Integration

**What it is**

A least-privilege GitHub Actions job that repeats the repository verification gate for pushes and pull requests to `main`.

**Why EchoClass uses it**

It makes the pre-Milestone-2 regression gate repeatable outside one developer machine.

**Where it is implemented**

`.github/workflows/ci.yml`, using official checkout/setup-node actions, npm caching, Node 24, and `contents: read` permission.

**How it is tested**

The YAML commands are first run locally. Remote success is reported only after observing the actual Actions run.

**Limitations**

There is one Node version and no deployment job, coverage upload, badge, release, or secret-dependent provider test. Remote success is claimed only for an observed run tied to the exact pushed commit.

**Likely interview questions**

- Why use one Node version instead of a matrix?
- Why must a local PASS not be reported as a GitHub Actions PASS?

## Database normalization

**What it is**

Moving authoritative, repeatedly queried scientific concepts from an opaque JSON document into typed relational columns and relationships.

**Why EchoClass uses it**

Authorization, validation, yield calculation, grouping, idempotency, review and provenance need enforceable/queryable values rather than duplicated `data_json` state.

**Where implemented**

Migration 2 creates `experiment_records`, `groups` and supporting constraints; `SqliteProvenanceStore` maps them to the compatible domain record shape.

**How tested**

Fresh/legacy migration tests verify scientific values, ownership, labels, IDs, timestamps, review projection and extension metadata.

**Trade-offs**

The schema has more columns and mapping code. Only optional extensions remain JSON to avoid a speculative sparse model.

**Limitations**

Users/enrollments are not fully normalized, and the current workflow supports one real experiment type.

**Likely interview questions**

- Which fields stayed JSON, and why?
- How did you avoid breaking the existing API?

## Schema migrations

**What it is**

An ordered, recorded sequence that transforms an older database into the schema expected by the application.

**Why EchoClass uses it**

Inline `CREATE IF NOT EXISTS` and ad-hoc column checks could not prove atomic, once-only legacy conversion.

**Where implemented**

`src/infrastructure/database/migrations/` and `schema_migrations`.

**How tested**

Tests cover fresh, legacy, already-current, exact-prefix ledger enforcement, ledger immutability, strict invalid-data preflight, count/integrity verification and injected failure rollback.

**Trade-offs**

Migration code must be maintained indefinitely and tested against real older shapes.

**Limitations**

There is no automated down migration; rollback uses a verified backup and prior application.

**Likely interview questions**

- Why insert the migration row inside the same transaction?
- How do you detect a renamed applied migration?

## Transactions

**What it is**

An atomic boundary in which all writes commit together or all roll back.

**Why EchoClass uses it**

Schema conversion, JSON snapshot import, record update, review event/projection and analysis run/input linkage must not be half-written.

**Where implemented**

The migration runner and focused transaction helper in `SqliteProvenanceStore`.

**How tested**

Injected migration, missing review target and missing analysis input tests verify rollback leaves no accepted partial rows.

**Trade-offs**

Write transactions hold SQLite locks and therefore remain intentionally narrow.

**Limitations**

They are local SQLite transactions, not distributed transactions across an external provider.

**Likely interview questions**

- Which workflows need transactions and which reads do not?
- Why use `BEGIN IMMEDIATE`?

## Foreign keys

**What it is**

Database-enforced references between creators/classes/groups, records/reviews and analysis inputs.

**Why EchoClass uses it**

Provenance links must not silently point to missing rows.

**Where implemented**

Migration DDL, with `PRAGMA foreign_keys=ON` verified during SQLite startup.

**How tested**

Tests reject a missing creator, run `PRAGMA foreign_key_check`, reject cross-record review links, and prove soft-archived records retain their history.

**Trade-offs**

Write order and deletion policy become stricter; user upserts must not delete referenced rows, and canonical observations require an explicit archival state.

**Limitations**

Unresolvable legacy creator/reviewer IDs remain nullable and explicitly marked rather than fabricated.

**Likely interview questions**

- Why use `RESTRICT` for reviewed records?
- When is `SET NULL` defensible for provenance?

## Unique constraints

**What it is**

A database guarantee that one key or scoped key cannot appear twice.

**Why EchoClass uses it**

Application pre-checks alone cannot prevent concurrent offline-idempotency races.

**Where implemented**

Primary/unique keys plus `uq_experiment_records_offline_submission` on creator, class and non-null client ID.

**How tested**

The same actor/class/key conflicts while another actor may reuse the client key safely.

**Trade-offs**

Every insert maintains the index and callers must resolve a race winner after conflict.

**Limitations**

The JSON adapter cannot enforce equivalent concurrent uniqueness.

**Likely interview questions**

- Why is the idempotency index partial?
- Why is the primary record ID not the offline key?

## SQL indexes

**What it is**

Additional ordered structures that accelerate specific filters/orderings at write/storage cost.

**Why EchoClass uses it**

Class listing, concentration grouping, review history, reviewer audit and provenance reverse lookup are concrete access patterns.

**Where implemented**

Migration 2 index DDL documented in `docs/data-model.md`.

**How tested**

`EXPLAIN QUERY PLAN` confirms the class/time query can select its intended index.

**Trade-offs**

Indexes consume space and slow writes, so no index is added to every column.

**Limitations**

No benchmark or production query distribution has been measured.

**Likely interview questions**

- How did you choose index column order?
- Why is query-plan use not a performance claim?

## Append-only event/history design

**What it is**

Each review decision is a new immutable row; a newer decision does not rewrite the older one.

**Why EchoClass uses it**

Scientific selection decisions need an auditable human history.

**Where implemented**

`record_reviews`, `review_event_order`, immutability triggers, `ReviewService`, and the trigger-maintained current-state projection.

**How tested**

Two decisions remain queryable in monotonic insertion order, the effective pointer is deterministic even when timestamps tie, SQL update/delete/replace/upsert is rejected, and role/class authorization remains intact.

**Trade-offs**

History grows and consumers must distinguish event history from the compatibility projection.

**Limitations**

Legacy data can supply only one explicitly marked projection, not missing historical events. Trigger ownership is specific to SQLite; JSON compatibility mode does not claim equivalent guarantees.

**Likely interview questions**

- Why retain a current-state projection?
- How do you prevent the projection and history diverging?

## Scientific provenance

**What it is**

Evidence linking canonical observations, human decisions and future analysis inputs/results without conflating them.

**Why EchoClass uses it**

Review and derived results must be traceable to the data and decision state actually selected.

**Where implemented**

Normalized records, append-only reviews, `analysis_runs`, `analysis_inputs`, snapshots and hashes.

**How tested**

Legacy conversion, review linkage, cross-record rejection, exact input linkage, schema validation, immutability, explicit corruption errors and post-edit snapshot stability tests.

**Trade-offs**

More storage and explicit workflow metadata are required.

**Limitations**

No analysis algorithm, scientific validation study or reproducible run orchestration exists yet.

**Likely interview questions**

- What is the difference between raw, canonical, derived and analyzed data?
- Which provenance facts cannot be reconstructed from the legacy schema?

## Analysis input snapshots and hashes

**What it is**

An immutable serialized copy of selected record/review state plus integrity identifiers at run creation.

**Why EchoClass uses it**

Live rows can change after an analysis, so links alone are insufficient for later reconstruction.

**Where implemented**

`analysis_inputs.snapshot_schema`, `record_snapshot_json`, optional review snapshot, input hash and run dataset/configuration/code metadata.

**How tested**

Changing the live oil mass after run creation leaves the stored input unchanged; missing input linkage rolls the run back.

**Trade-offs**

Snapshots duplicate data and require a future canonical hashing/serialization specification.

**Limitations**

Current hashes are caller-supplied foundations; no production canonical serialization, hashing or analysis service is implemented.

**Likely interview questions**

- Why snapshot instead of adding record-version tables?
- What must be canonicalized before hashing?

## SQLite trade-offs

**What it is**

A transactional embedded relational database stored in one local file.

**Why EchoClass uses it**

It matches the current single-process classroom deployment and provides migrations, constraints, indexes and transactions with low operations overhead.

**Where implemented**

Node.js 24 `node:sqlite`, migration modules and infrastructure repositories. The same supported major is pinned in `engines`, `.nvmrc`, Docker and CI.

**How tested**

Real in-memory/file-backed SQLite tests plus HTTP integration and smoke workflows.

**Trade-offs**

Simple deployment and strong local integrity trade against distributed writes and managed-service operations.

**Limitations**

EchoClass does not claim PostgreSQL support, horizontal scaling, JSON-mode equivalence, `node:sqlite` production readiness or deployment readiness.

**Likely interview questions**

- When would SQLite stop being appropriate?
- Which repository boundaries help a future adapter without pretending migration is free?

## Milestone 2A.2 provenance closure

**What it is**

A corrective boundary pass that freezes historical migrations and makes measurement, import, review, snapshot, original-submission, idempotency and run-identity claims enforceable end to end.

**Where implemented**

The version-keyed migration preflight, migration 004, validated persistence/import commands, snapshot-v1 validators, SQLite repository, archived audit lookup and adversarial/integration suites.

**How tested**

Migration fingerprints and v2/v3 upgrades; real HTTP-to-database measurement round trip; invalid repository science/yield/review attempts; malformed stale JSON and atomic import restart; raw projection, snapshot, original-submission and run-identity mutations; effective review binding; archived authorized audit access.

**Trade-offs and limitations**

SQLite triggers and validation duplicate some application intent to protect raw persistence paths. JSON mode remains weaker, `node:sqlite` is retained behind an adapter, and no production hashing specification, general record version history, Python analytics or deployment-readiness claim is added.

## Milestone 2B.1 questions

- **Why not loop single-record create?** Its record and audit operations are separate. CSV requires group creation, every canonical record, every mapping, completion and the one success audit to share the same connection and COMMIT. A later row failure must roll everything back.
- **Why hash the BOM too?** The receipt identifies received bytes, not normalized values. BOM, quote spelling and CRLF changes should yield a different digest and conflict under a reused token.
- **Does a hash mean the original is saved?** No. Only SHA, byte count and completion facts are retained. Re-uploading matching bytes later cannot establish earlier storage custody or observation truth.
- **Why stable class_id?** Display names and user class assignments can change. The original idempotency namespace must not move with a rename or record correction; current permissions are independently rechecked.
- **Why can archived records replay?** Immutable mappings are read without an active-only filter. A retry returns original IDs and never restores or duplicates archived records.
- **How do two tables prevent half batches?** Rows reference a not-yet-inserted parent through a deferred FK. The parent insert requires exactly contiguous rows with valid canonical ownership. Missing parent fails COMMIT; completed parent and mappings cannot be changed or replaced. Audit failure also rolls back the whole transaction.
- **Why protect spreadsheet text only on output?** Import preserves valid source observations. Visible text: prefixes belong to a potentially executable spreadsheet display context, while typed scientific numbers remain numeric and platform data remains unchanged. No universal spreadsheet certification is claimed.
- **Why is export not Python authority?** It includes current active records with their actual review projection and display transformations. Python must consume the established sealed analysis input contract with review binding, not infer approved inputs from this download.
- **What did the LLM decide here?** Nothing in CSV parsing, quality rules or transaction outcomes. Those are deterministic library/domain/database operations.
- **How was integrity tested?** Real SQLite triggers fail after earlier writes, including a deferred-FK COMMIT failure; snapshots prove rollback. Independent child processes race the same token, disk reopen simulates lost responses, and raw SQL tests exercise immutable seals. Removing the completeness trigger inside a rolled-back synthetic fixture demonstrates why FK/unique checks alone cannot enforce the claimed row count.

### Two failures the first CSV tests missed

- **Can finite numbers yield infinity?** Yes. Dividing by a sufficiently small positive mass overflows. Check the result using the same operation order as production; do not invent a scientific minimum solely to hide a machine-number limit. Test the shared validator, actual import and direct database boundary.
- **Can an idempotent endpoint still create duplicates?** Yes, if the page forgets the token and creates another. Test the actual sequence: commit A, lose the response, preview B, return to A, reload and retry. Our corrected page retains each combination's identity. Cleared browser storage still cannot recover an unknown token automatically.
- **Did AI assistance disappear from this work?** No. The implementation and independent agent review are documented. Application claims should describe what you can demonstrate and explain, rather than claiming unaided authorship or invented use by real classes.

## Milestone 2B.2 questions

- **Why save the file before the database row?** SQLite cannot atomically commit an external file. Syncing and publishing bytes first keeps ordinary successful metadata from pointing to a file that was never published. A later database failure can leave an orphan, which is retained because an uncertain commit is not proof it can be deleted.
- **Why use a UUID and retain archived bytes?** Each upload owns one immutable file. This avoids shared references and cleanup races while keeping historical evidence readable to authorized teachers. Fixed retained-file and byte limits bound ordinary use; orphan storage is a documented maintenance boundary.
- **What does re-uploading an old CSV prove?** Its bytes match the digest/length received by the original import, and the later file was received now. It does not prove the platform retained it earlier.
- **Why authorize again after reading?** The account or target can change while filesystem work is pending. Checking before read alone could disclose bytes after revocation. The route also checks synchronously after its last await, directly before sending headers.
- **Why isn't copying citrus.db a backup?** Committed changes may still be in WAL. A consistent snapshot is needed, then every immutable object referenced by that snapshot, including archived evidence. A completion marker is meaningful only after content verification and sync.
- **Why refuse a partial restore at startup?** A command can be interrupted after copying the database but before its files. Starting that directory would make an incomplete recovery look like a healthy application. The progress marker blocks both storage modes until verification completes.

## Scientific computing and retrieval — current implementation

**What it is**

Python produces sealed descriptive/bootstrap/regression reports. Node validates their identities and results. Report cards cite those saved values; project-guide search returns exact Markdown excerpts using SQLite FTS5/BM25. The two evidence sources have different purposes and are labeled separately.

**Why EchoClass uses it**

A later edit must not rewrite an earlier result. A retrieved explanation must expose its source and limitations. Domain correctness takes priority over fluent but unverified generated prose.

**Where implemented**

`analytics/echoclass_analytics/analysis.py`, `src/application/scientific-service.ts`, `src/domain/grounded/evidence.ts`, `src/domain/grounded/retrieval.ts`, and `src/infrastructure/database/sqlite-document-retriever.ts`.

**How to test it**

Run `npm run test:python`, `npm run eval:grounded`, `npm run eval:retrieval` and `npm run test:integration` with the locked Python environment. The HTTP test preserves an old result across corrections/restart, then refuses access after account revocation.

**Likely interview questions**

- Why group-mean regression and concentration-level LOOCV? The fixed protocol makes each tested concentration equally influential and avoids treating parallel observations as independent held-out concentrations. It differs from the original all-record fit plan; it does not establish biological independence or generalisation.
- What does BM25 rank? Lexical overlap with document-length/term-frequency weighting. SQLite's built-in score sorts ascending. It is not a probability that an answer is true. English words and Chinese bigrams are pre-tokenized consistently; a coverage threshold can reject both irrelevant and legitimate paraphrased questions.
- Is this full RAG? No. Retrieval is implemented, but this endpoint returns exact extracts without model-generated claims. The older optional model only sorts report cards. Source selection still needs evaluation; exact copying alone cannot prove relevance.
- Why an in-memory index? Twenty bundled sections are small, public project documentation. Rebuilding avoids schema churn and guarantees a matching current corpus hash. User-uploaded/private material would require a new authorization, persistence, provenance and ingestion design.
- Why no question log? Free text can contain identities or secrets. Audits keep outcome, source IDs and answer/corpus hashes; supported PII redaction is not complete anonymization. There is no outbound transmission here even when a name is not recognized.
- Does 42/42 establish model accuracy? No. These are developer-authored regression cases, including cases used during development. There is no held-out set, live model, independent human rubric or genuine classroom benefit measurement.
