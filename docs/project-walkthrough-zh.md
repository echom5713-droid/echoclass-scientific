# 怎么把 EchoClass 讲清楚

这份笔记用来帮助理解代码和准备演示。申请材料里的措辞应建立在你实际掌握、亲自验证过的部分上。先把一个数据流程讲顺，再谈用了哪些技术。

## 从一个具体问题开始

课堂实验的数据常常来自表格、手工输入和照片。麻烦不只是算平均值：谁提交了数据？教师后来改了判断，还能知道分析当时用了哪一版吗？网络中断后再点一次，会不会多出一组实验？一张照片的名字没变，内容还是原来那张吗？

EchoClass 用实验课作场景，练习的是数据系统共有的问题：验证、权限、事务、重试、历史证据和可复现计算。这些能力也适用于调查数据、运营记录和其他研究工作，不要求未来一直从事化学软件。

不要用“解决了科研数据真实性”概括项目。程序能保留和检查提交证据，不能证明操作者确实完成了实验。

## 先跟着一次 CSV 导入走

1. 页面选择一个已有班级，读取文件字节，然后请求预览。`src/http/routes/csv-routes.ts` 只处理 HTTP 契约；`src/application/csv-service.ts` 安排验证与调用。
2. 解析器读取 UTF-8、固定表头和逻辑行。领域校验检查数据范围。预览可以指出错误，却不会创建记录。
3. 提交携带文件摘要和本次导入标识。服务器重新计算摘要，重新验证权限和内容。摘要相同只能说明字节相同，不能代替权限检查。
4. `src/infrastructure/database/sqlite-csv-repository.ts` 在一笔同步事务中创建组、实验记录、行映射、完成回执和审计。如果后面一行失败，前面已写的行也会回滚。
5. 响应丢了再重试，服务器凭“上传者＋班级＋导入标识”找到旧回执，返回原来的记录 ID。用户明确开始另一次导入，才会使用新标识。

可以把“原子性”和“幂等性”分开解释：原子性解决一批数据只写了一半；幂等性解决同一次操作被执行了两遍。它们不是同一个保证。

## 两个适合深入讲的真实故障

### 两个有限数，为什么会算出无穷大？

第一版分别确认两种质量都是有限数，但 `1 / 1e-308 * 100` 仍会超出机器能表示的范围。数据进库后，表格导出遇到无限产率就整批失败。原来的正常输入测试没有覆盖这个组合。

修复没有凭空规定一个“科学上合理的最小质量”，而是检查同一计算顺序下的结果能否表示。共享校验、持久化入口和新增 Migration 014 各自守住相应边界。遇到已经存在的坏值，迁移会停下来，要求根据真实测量修正，不能帮人猜数据。原始提交快照保留。

想看证据，运行 `node --import tsx --test tests/finite-derived-yield.test.ts`。重点读测试如何证明“整个导入零写入”和“修正当前数据没有改原始提交”，不要只记通过了多少项。

### 服务器幂等，页面为什么仍会重复导入？

原页面只留一个重试标识。提交 A 成功但没收到响应，再预览 B，就覆盖了 A 的标识。回到 A 时服务器收到的是一个新操作，按合同正确地创建了另一批记录。

现在按用户、班级、格式和文件摘要分别保留标识，并让用户显式确认新导入。测试执行实际客户端脚本，重现“提交 A → 丢响应 → 预览 B → 回到 A → 刷新重试”的顺序。修复后返回同一批次，新增零条。

这说明测试服务器接口还不够。一次用户操作跨越页面状态和服务器，两个部分都要保留同一个操作身份。浏览器存储被清空后，页面仍不能凭空恢复未知标识；不要把有限的恢复能力讲成永远不会重复。

## 为什么保存快照，而不只保存记录 ID？

记录 ID 指向的是一条会被修正的数据。分析完成后，教师可能更正质量，也可能追加一次审阅。如果报告每次都重新读取当前记录，它展示的就不一定是当时计算的输入。

项目已有封存的分析输入：实验快照、审阅快照、两者的绑定方式、顺序和版本信息。后来的合法修改保留在当前记录中，旧分析输入不随它变化。旧资料缺少能证明的历史信息时，要降低可复现性分类，不能补写一段看似精确的历史。

beta.15 审查版把这个基础接到了 Python 计算与报告。Node 在同一次事务中捕获数据、算摘要并登记任务，Python 只接收封存内容，不连接数据库。结果回到 Node 后，还要核对数据摘要、方法配置、运行身份、字段类型和有限数值，才会成为已完成报告。对应里程碑的结果文档仍是验收依据。

## 科学分析最值得讲清楚的三个选择

第一，教师“纳入”不是删除异常值的同义词。所有候选记录连同当时的审阅一起封存，只有明确纳入的记录进入主分析；IQR 只做标记，不暗中移除已经纳入的观测。这样可以解释一次分析为什么用了这些数据，而不是事后挑出最好看的曲线。

第二，模型使用四个浓度组的均值，给每个浓度同样的权重。交叉验证每次留出整个浓度组，用另外三个浓度拟合，再预测留下的那一组。它检验的是跨浓度预测，不是把同一浓度的几条记录随机分到训练和测试两边。端点 0% 和 4% 的留一预测属于外推，报告也会注明。

第三，“实测平均得率最高”与“模型提示的待验证浓度”是两回事。前者只比较已测组，真实并列必须保留；后者还要求曲线凹向下、顶点位于已测范围内，而且删去任意一组后仍满足这些条件。通过这些检查也不等于证明了最优浓度，只是提供下一次实验的候选。Bootstrap 区间同样有前提：把每条记录视为独立重复，而当前数据库不能证明这个前提成立。

## 服务突然退出时，任务怎么办？

一次任务最多两次尝试，每次有不同的执行标识。旧响应晚到时，数据库会检查它是不是当前尝试，不能覆盖新的状态。服务重启前，Node 和 Python 共同持有同一个操作系统文件锁；第二个实例拿不到锁，就不能接管仍在执行的任务。关闭时先确认 Python 进程退出，再释放父进程的锁描述符。

这部分有一个具体的故障测试：杀掉父进程后，它的日志管道也可能消失。最初的实现先写日志、再退出；写日志抛错会阻止退出。现在退出放在 `finally` 中，日志失败也不能留下失去监督的计算进程。这个例子比泛泛地说“做了容错”更能说明你理解了什么。

可先运行 `npm run scientific:demo` 看合成示例，再运行科学流程集成测试。集成测试会建立报告、改动并归档原记录、复算旧报告、模拟一次中断后恢复。合成样例展示方法与程序行为，不是实验有效性或真实教学效果的证据。

## 附件和数据库为什么不能一起回滚？

数据库事务只能管理数据库。程序先把文件写完、同步到磁盘，再发布到不会覆盖旧文件的位置，最后提交元数据。如果数据库提交失败，文件可能已经在那里。这个版本保留这种孤儿文件，不根据一次报错猜测删除；有时提交其实成功了，只是响应没有回来。

归档也只改变可见状态，不直接删文件。因此备份必须连已归档的附件一起保存。备份先取得一致的SQLite快照，再按快照里的引用复制文件、核对摘要，最后写完成标记。恢复则使用全新目录；中途被打断时，应用看到标记就拒绝启动。

你可以用一个损坏附件解释摘要的作用：它能让程序发现字节变了，并拒绝给用户错误的文件；摘要本身不能把原件变回来。恢复仍然需要一份完好的备份。

## 为什么不用一个更大的技术栈？

这个项目目前的数据规模和运行方式适合一个 Node 应用与 SQLite。把数据库与文件操作放在基础设施层，把业务顺序放在应用层，可以分别测试“允许做什么”和“实际怎么保存”。路由不直接写 SQL，因此改动 HTTP 输入格式时，不必把事务规则复制一遍。

这不表示换 PostgreSQL 是免费的。SQL 方言、并发模型、迁移和备份都要重新验证。同样，保留一个接口也不能证明项目已经支持横向扩容。

## 报告解释里的 AI 到底做了什么？

beta.16 没有把整份报告塞进聊天模型。读者选择一个主题，程序按固定映射取出保存的报告字段和方法说明，每段解释都附有可展开的依据。科学结果摘要对应计算结果，证据包摘要对应本次取出的字段，解释摘要还包含说明顺序；三者回答的是不同问题。

默认流程不用外部模型。可选模型只收到主题与固定卡片的标题、标识，返回一个排序；它不能改数字、写结论或删除限制说明。服务器要求返回值恰好包含全部原卡片，伪造、重复、遗漏或超时都回退到本地顺序。这个设计的代价也要讲清楚：它不是自由问答或论文检索，语言灵活性有限，尚未证明模型排序比固定顺序更好。

可以亲自试三个反例：给接口加一个自编的引用字段，应被拒绝；模拟模型删掉限制卡片，应回退；等待模型时停用账号，结果不能再返回。对应测试是 `grounded-evidence`、`grounded-ranker` 和 `grounded-service`，离线评测命令为 `npm run eval:grounded`。通过率仅描述这些合成合同测试，不是实际模型准确率，更不是教学效果。

这部分最值得讲的不是“接入了大模型”，而是你怎样限制外部组件的权限，以及一个回答如何追溯到当时的保存值。以后若引入自由文本生成、文献或语义检索，需要另外验证来源可靠性、引用是否支持句子、拒答质量与隐私边界。

## 演示前自己做这五件事

- 用隔离的合成数据，分别做一次正常导入和一次中途失败的导入，观察数据库记录数和回执。
- 对照一项权限测试，说出被拒绝的是哪一个当前条件，不能只说“系统有登录”。
- 修改一条当前记录，再读取已封存的旧输入，解释为什么两者不同而且都合理。
- 读一个故障回归测试，先猜删掉对应保护后会发生什么，再在临时分支验证；不要改真实数据或已发布迁移。
- 用两分钟说明已完成的能力、尚未完成的能力和一个仍然存在的限制，不背功能清单。

演示、测试和代码都应能对应到真实提交。合成样例不能叫真实实验结果，测试次数不能叫用户数量，AI 协助生成和修改代码也不应该包装成完全独立完成。你能亲自复现、解释并修改其中的关键流程，才是这段项目经历最有说服力的部分。

## 资料检索与 RAG 差在哪里？

beta.17 新增的检索读的是项目自己的 Markdown 指南，不是数据库里的学生备注，也不是用户上传的实验文件。每个片段有来源、版本和内容摘要。英文按词处理，中文拆成相邻的两个字，再放进 SQLite FTS5。BM25 负责排序；它比较的是词面相关程度，不能判断一句话科学上是否正确。

这次第一次跑 42 道题时，有一个英文问题漏检。问题问 IQR 标记能否自动删数据，而英文说明用了另一种表达；补齐对应的第一方说明后回归通过。这个例子正好说明：测试集参与开发之后，就不能把通过率包装成未见问题上的准确率。中文同义表达也可能漏检。

页面显示原文，不让模型改写成结论。你可以输入“bootstrap 区间怎么计算”、一个资料外的问题、一个让程序忽略规则的指令，再检查原文、拒答和审计记录。姓名、学号、邮箱等可识别模式会先被移除，原问题不进入持久日志；不要声称正则表达式能识别所有个人信息。

对面试官可以准确地说：“我实现了版本化资料的词面检索和可核验引用，并设计了离线评估。当前抽取式路径不生成新的模型主张，因此不能叫完整的生成式 RAG。”下一阶段如果让模型写答案，就必须检验每条主张是否被所引原文支持，而不能只检验引用 ID 存在。

## 从一个具体结果开始讲清楚项目（beta.18）

先按 `docs/reproducible-case.md` 在本地运行 `npm run scientific:demo -- --text`。这一份 fixture 有 20 条合成记录：0%、1%、3%、4% 四个浓度，每组五条。1% 和 3% 的均值得率都为 9%；拟合给出约 2% 的候选点。要能解释为什么不能直接说“2% 就是最佳实验条件”，以及为什么这个例子不能证明真实提取效果。

接着读 `public/offline-submission.js` 和 `tests/offline-submission-client.test.mjs`。在“服务器已经保存，但浏览器没有收到回执”的情形下，重试必须保留原标识。再看 `src/http/routes/experiment-routes.ts` 中 `/api/record-submissions` 如何核对当前账号与班级。只在浏览器里保存姓名，不能保证原始记录归属正确。

这里还有一个命名上的历史负担：`synced_from_offline` 在新版学生路径中表示经过本地暂存渠道，不一定意味着当时断网。这一版选择保留已发布迁移，因此说明和界面不能据此编造网络故障历史。

最后用 `/engineering` 对照源代码：原始提交、教师决定、封存输入分别在哪里保存？一个哈希能检出什么变化，又不能证明什么？如果你暂时答不上其中一个问题，就沿链接运行对应测试；先理解一个真实失败和修复，再扩展到整个系统。

## 两个浮点数反例（beta.19）

`[3,5,6,7,10]` 的 Q1=5、Q3=7，上界正好为 10。严格大于上界才算异常，因此 10 不应被标记。原先先缩放再计算，会因为浮点舍入把边界稍微移低。现在按封存十进制数做精确分位数和比较，同时保留“只大一点也要标记”的测试。

另一个例子是 `[0.10,0.20]` 与三组 `[0.15,0.15]`。四组真实十进制均值相同，原先却在不同计算路径中产生微小差异，并报告 R²=−8.5。修正统一使用精确组均值，先中心化再拟合；常量响应的 R² 明确不可用。不要把修正理解成“负 R² 一律改成零”。

可以沿 `docs/scientific-roundoff-review.md` 自己复现，解释为什么这会更新结果哈希，却不能改写旧报告的代码身份。再读输入校验的历史兼容测试：改一个公共校验函数也可能改变旧迁移的行为，因此新封存的校验规则与历史读取规则要分别处理。

## 四个点一样，最优条件为什么还能完全不同？（beta.20）

先运行 `npm run scientific:study -- --text`，再看 `docs/method-study.md` 的两条曲线。二次函数 `q(x)=6+4x−x²` 与 `f(x)=q(x)−x(x−1)(x−3)(x−4)` 在 0、1、3、4 上相等，因为相减的乘积在那里都是零。到了 2，前者是 10，后者是 6。这个反例不需要背复杂术语，代入就能验证。

程序给这两种情况加入相同的误差，生成完全相同的观测与封存摘要。因此计算、交叉验证、候选点也完全一样。差别只在程序看不到的真实响应。留一浓度验证能检查对已测浓度的预测，却不能排除两个函数在未测区间出现不同形状。这是数据没有提供足够信息，不是靠再加一个哈希就能解决的软件问题。

读表时分清两个指标：留出折的目标是带噪声的组均值，未测网格的目标是合成函数的无噪声真值，所以两列不能当成同一种泛化误差。端点的留出预测属于外推。十二个固定种子是一个可复跑的小面板，不是覆盖所有实验环境的统计保证。

再看常数情形：系统有两次仍返回了二次模型候选，但真实函数没有独特峰顶。它的零遗憾只是因为所有位置的真值都一样。不要把“候选稳定”“遗憾为零”讲成“找到了真正的峰值”。这个项目能有说服力的地方，是你能把这些容易混淆的结论分开。

容器解决另一种复现问题：别人是否拿到了正确的 Node、Python、依赖、文件和持久化设置。它仍然共用主机内核，因此容器化不自动等于跨主机逐字节相同。读 `docs/scientific-deployment.md`，自己解释为什么需要 init 父进程、为什么新数据卷不能遮住检索资料，以及为什么重启后要复算原来的封存报告。

亲自复现之后，试着用三分钟回答：研究问题是什么？简单基线为什么必要？反例揭示了什么？还需要怎样的新实验？你修改过、理解了哪些部分，哪些实现借助了 AI？这些答案要来自实际掌握，不能把这份笔记当成已经完成独立研究的证明。

## 发现模型分不清以后，下一次测哪里？（beta.21）

打开 `/engineering#next-measurement`，先把浓度从 2 调到 1。两个指定函数在 1 上的预测都等于 9，因此不论重复一次还是五次，都不能靠这些读数区分它们。重复可以让均值估计更准，却不能让原本相同的两个预测变得不同。

再调回 2：预测分别是 10 和 6。新研究在看到模拟结果之前，按两个预测的绝对差选择测量位置。给定相同的已知噪声，差距越大，越容易区分。这个例子中 2 是网格上的唯一最大值，也能用一个二次表达式证明它是整个区间的最大值。不是先跑很多方案，再挑表现最好的一次。

这里必须主动说出假设：两个函数及其参数已知，误差为已知标准差的正态分布，重复读数独立，误判成本相同，展示平均误判率时给两种假设相同先验概率。样本均值的标准差是 `sigma / sqrt(n)`，判别线在两个预测的中点，所以误判率由“半个预测差距 / 均值标准差”决定。噪声标准差为 2 时，在浓度 2 测一次的理论误判率约 15.87%，独立测三次约 4.16%。这是模型里的概率，不是项目在真实课堂上取得的正确率。

尤其不要混淆前后两个研究：上一版用有界均匀误差检查生产分析；这一版用新的、未截断的正态误差研究一个可推导的判别问题，不使用真实记录，也不调用生产科学工作进程。少数模拟配置恰好没有误判，也不能说真实误判概率为零。

最后追问自己：补上 2 后是不是就找到了真实曲线？仍然不是。`g(x)=q(x)−x(x−1)(x−2)(x−3)(x−4)` 在五个整数点都与 `q` 相等，其他位置却不同。新实验解决了原来的两假设问题，没有解决任意函数的识别问题。能把“数据不足—提出新测量—量化条件—保留新局限”讲成一条完整推理，比背诵一组术语更有价值。
