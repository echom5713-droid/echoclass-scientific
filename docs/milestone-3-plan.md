# Python scientific analysis — Milestone 3 contract

Date: 2026-09-05. **Implementation in progress; acceptance is pending.** Milestone 2B.2 passed its release boundary at beta.14. This milestone uses forward migration 016; migrations 001–015 remain frozen. The exact cross-language fields are in [scientific-protocol.md](scientific-protocol.md).

## Outcome and scope

A teacher can select a class, request an analysis, and read a reproducible explanation of its recorded yield results. Node authorizes and seals the actual input; Python computes from those immutable snapshots; Node validates and saves one terminal result; a small report explains the methods and limitations.

Keep the existing Node application, SQLite and repository/service boundaries. Add one Python package containing a pure analysis function and a thin, stateless FastAPI application on the same machine. Node owns the only durable queue. Python has no database connection, classroom authorization system, upload store, persistent job queue or public browser endpoint. No Redis, Celery, Kubernetes, database migration to another engine, UI framework rewrite, OCR, model training or LLM explanation is included.

The target stack is Python 3.12, FastAPI/Uvicorn, Pydantic, pandas, NumPy, SciPy, statsmodels and pytest. pandas prepares an explicitly typed table after validation; NumPy/SciPy/statsmodels implement the calculations. The implementation environment has Python 3.12 with NumPy 2.3.5, pandas 2.2.3, SciPy 1.17.0, statsmodels 0.15.0, Pydantic 2.13.4, FastAPI 0.141.1, Uvicorn 0.52.4 and pytest 9.1.1. Pin and verify the actual tested environment in project CI; an available surrounding runtime is not a dependency lock.

The primary endpoint is the sealed `yield_percent`, in percent, grouped by `nh4cl_concentration` at 0, 1, 3 and 4 percent. Use the stored, canonical two-decimal yield; do not silently recompute a higher-precision outcome in Python or alter the existing legacy report. Antibacterial endpoints, multivariable models, significance testing, comparisons between classes and automatic optimization are outside v1.

## Existing foundations and the narrow addition

The current `AnalysisRepository` and `SqliteProvenanceStore` already provide immutable record/review snapshots, binding modes, contiguous nonempty input ordinals, input sealing, exact/legacy classifications and immutable terminal results. JSON compatibility mode does not support this provenance workflow and continues to return an explicit unavailable error.

Three facts govern the new implementation:

1. `createAnalysisRun` captures live rows inside a transaction but accepts caller-supplied `input_hash` and `dataset_hash`; it currently checks identifier syntax, not a cryptographic relationship to the snapshots. A service-side read/hash followed by the existing method would race with a correction or new review.
2. Current input INSERT guards require the snapshot and effective review to match the current record at selection. They must remain in force. A historical snapshot cannot be copied into a new run through that creation path.
3. The existing state machine allows pending to running/completed/failed, running to completed/failed, and same-state updates. Completed/failed content and completion time are immutable. Failed cannot return to running. Legacy or incomplete datasets cannot be promoted into an executable exact dataset.

Add a narrow `ScientificAnalysisRepository`, backed by SQLite, for the production workflow. Reuse the existing snapshot validators and durable-review checks. If extraction of a shared snapshot capture helper is needed, keep it synchronous and preserve the old creation behavior and tests. Do not add a general transaction framework or accept arbitrary caller snapshots.

| Proposed repository operation                   | Responsibility                                                                                                                                         |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `createScientificRun(context, command)`         | Fresh authorization, scoped request replay, current selection, canonical hashing, run/input insertion and sealing in one `BEGIN IMMEDIATE` transaction |
| `getScientificRun(context, runId)`              | Registered-run lookup, current authorization, checked result and public metadata                                                                       |
| `listScientificRuns(context, classId)`          | A bounded recent list under current class permission                                                                                                   |

| `recordAttemptFailure(runId, attempt, failure)` | Bounded operational metadata update while running; preserve the previous attempt summary                                                               |

| `readScientificInputs(runId)`                   | Require registered scientific v1, sealed/exact input and recomputed hashes; reuse `listAnalysisInputs` validation                                      |

Use one small additive STRICT registration table, tentatively `scientific_analysis_requests`: `run_id` (primary/FK), `class_id` (FK), `requester_user_id` (FK), `client_request_id`, `request_fingerprint`. Enforce a unique requester + stable class + client token; forbid UPDATE, DELETE and replacement. Its registration guard requires a pending run with empty results, the linked creator, scientific configuration marker, sealed exact run, and the complete current active class cohort with matching snapshot class IDs. This registers only new scientific runs; never backfill a production-hash claim for old test or legacy runs.

The existing run stores immutable algorithm/configuration/code versions and the mutable-then-terminal result envelope. Store at most two operational attempt summaries in that envelope; no lineage graph, snapshot-copy exception, separate result database or open-ended attempts table is needed. Any additional forward guards apply only to registered scientific runs: running must have a valid current attempt; attempt numbers advance only 1→2 and closed attempt summaries cannot change; completed must contain the expected result schema and matching dataset/execution fingerprints; attempts cannot exceed two; existing terminal immutability remains authoritative. A pending run may fail before its first attempt for an authorization or integrity error. SQL can check shape and relationships, not prove that Python calculated correct statistics or that a supplied SHA-256 is true. Node and Python independently verify those bytes at execution boundaries.

## Selection, review and access

Creation is available only to current active teachers/admins. Teachers select their current class; admins may select any one class. Students do not create or read these class-level scientific reports in v1. Authorize through stable class IDs and current account facts, never client-provided labels. Report reads and reproduction must also authorize every captured record's current class, including archived records, so later reclassification cannot expose another class. Historical review evidence is checked against its durable event, not reinterpreted using the reviewer's present role.

Seal all current active records in the selected class as the candidate cohort, ordered by binary record ID, with one distinct record per ordinal. A reviewer decision is part of the snapshot, not fetched again to decide the historical result. No arbitrary record picking, exclusion editing or review omission control appears in the first UI. Bind the current effective review where one exists; use `none` only when no review exists. Do not emit `omit` in new scientific v1 requests. The general legacy API retains its existing binding behavior.

The only v1 inclusion policy is explicitly named `approved_only.v1`:

- Effective review `included`: include in the primary calculation, even if IQR flags it. Show the flag and the recorded human decision together.
- Effective review `excluded`: never include in the primary analysis.
- `normal`, `review` or no approving review: retain in the candidate manifest/report but mark `not_approved`; do not silently treat a diagnostic label as approval.
- An alternative policy that admits unapproved records requires a future explicit contract and clearly separate exploratory result. It is not a hidden default or a URL switch.

The report lists candidate, included and omitted counts, record IDs, binding modes and specific exclusion reasons. A teacher can use the existing review workflow and request a **new analysis**; an existing run never changes when a review changes.

No candidate records means a 422 response before creating a run, consistent with the nonempty seal contract. Invalid scientific/provenance snapshots abort creation with bounded record-level issues rather than silently dropping rows. A valid sealed cohort with no approved data, a missing concentration or too few repeats produces a completed report whose affected statistics are unavailable with reasons. Do not invent observations, imputations, positive control groups, independent repeats or zero-valued statistics.

## Atomic creation and durable request replay

The Node command supplies `class_id`, a 16–128-character `[A-Za-z0-9_-]` client request token and `approved_only.v1`; v1 freezes the analytical settings below rather than exposing tuning controls. Bound the command body to 16 KiB. Reject unknown fields and caller-supplied run IDs, snapshots, hashes, creator labels, timestamps or results. The request fingerprint covers the normalized user command, not later resolved code/environment versions, so a response retry remains stable across an application restart or upgrade.

Inside one synchronous write transaction:

1. Re-read the session/account and current class authorization; resolve an existing authorized request token before selecting fresh data.
2. For an existing token, compare the normalized request fingerprint and return the original run; conflicting requests return 409. Recheck current read permissions. A response retry never reseals changed live data.
3. For a new token, select the bounded class cohort, capture record/review snapshots, validate binding and provenance, serialize each snapshot to its actual database JSON representation, parse that representation, and compute JCS input/dataset hashes from those exact persisted values in the same transaction.
4. Resolve the deterministic default seed if one was not supplied, freeze the resolved analysis configuration and execution fingerprint, insert pending run and inputs, and seal the complete set using the existing SQL guards.
5. Insert the scientific request registration and one creation audit, then commit. Any failure rolls back the complete creation.

No await, filesystem write, network request or Python call occurs inside this transaction. A changed file name, live row or current review cannot influence an already registered request replay. The UI keeps its token until the response is known and uses explicit confirmation before starting a new analysis.

## Canonical bytes and cross-language hashes

Freeze the canonical format before implementing algorithms. Use JCS/RFC8785 with UTF-8, no BOM and no trailing newline. JCS fixes primitive serialization and recursive object-key sorting by UTF-16 code units; preserve Unicode strings without normalization, and serialize negative zero as zero. Reject duplicate JSON keys, lone surrogates, non-finite numbers and unsupported values. Optional fields are either present or absent according to the named envelope schema, never normalized differently by Node and Python. Canonicalization must not mutate the stored snapshot JSON. A small reviewed JCS implementation must pass the RFC vectors; ordinary sorted `JSON.stringify`/`json.dumps` is not an interchangeable substitute. [RFC8785](https://www.rfc-editor.org/rfc/rfc8785.html)

Define the hash preimages without self-reference:

| Hash                     | Canonical content                                                                                                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input_hash`             | `echoclass.scientific-input.v1`, snapshot schema, full record snapshot, full review snapshot or explicit null, review binding mode, omission reason or explicit null   |
| `dataset_hash`           | `echoclass.scientific-dataset.v1`, stable class ID, ordered entries of ordinal + record ID + input hash                                                                |
| `execution_fingerprint`  | `echoclass.scientific-execution.v1`, dataset hash, complete resolved analytical configuration, algorithm/code versions and expected dependency-environment fingerprint |
| `scientific_result_hash` | Versioned scientific result only, including methods/availability/reasons; excludes request IDs, run IDs, attempt timing and report rendering time                      |

Use lowercase SHA-256 hex with a consistent `sha256:` prefix in persisted hash fields. Existing fields can hold this format; older arbitrary hash strings do not become v1 automatically. Store the execution fingerprint alongside the analytical settings in the run configuration envelope, but exclude that fingerprint field from its own preimage. Node computes the scientific-result hash after strict validation and JCS serialization of the returned scientific result. Python returns measurements and fingerprints; it does not claim that its ordinary JSON serializer produces JCS result bytes.

Transport the exact canonical input strings, dataset-manifest string and execution-manifest string within a bounded internal request envelope. Python hashes each string's UTF-8 bytes **before parsing that string** and compares the supplied input/dataset/execution digests. After parsing, it verifies the ordered mapping, matching dataset reference and complete algorithm/configuration/environment contract before calculation. This avoids requiring a second canonical serializer to reproduce JavaScript's floating-point output. It also makes it possible to supply the same bytes to the standalone Python reproduction command. Byte preservation and semantic validation are separate checks.

After byte verification, parse through strict Pydantic models and reject unknown core fields, invalid dates/bindings, numeric strings, booleans in numeric positions, duplicate IDs/ordinals and non-finite values. Preserve the allowed JSON metadata object without using it as a source of measurements. Do not use pandas coercion or `dropna` to make an invalid input appear valid. Use strict JSON output (`allow_nan=False`); undefined statistics are explicit null plus a machine-readable reason. [Pydantic strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/), [Python JSON behavior](https://docs.python.org/3/library/json.html)

Golden fixtures must cover key order, Chinese and supplementary Unicode keys, escaping, null versus absent fields, zero/negative-zero policy, exponent notation, subnormal finite values and the largest finite double. Mutating a measurement, review decision, binding mode, input order or byte must fail or change the specified hash. Changing an operational run ID/time must not change the dataset hash. Use synthetic fixtures only.

## Scientific methods and unavailable results

All primary statistics use only approved snapshots. Retain their actual two-decimal yield values. Beta.19 computes means and ordered summaries with exact rational arithmetic on the sealed decimal values, then converts displayed values to float64 once; SD, MAD and bootstrap retain scaled float64. Regression centres exact group means before float64 fitting. Protect intermediate sums/squares from overflow by documented scaling, and validate every emitted number. The [current protocol](scientific-protocol.md) records the correction and precision boundaries. A representational failure yields an explicit unavailable/error reason, not clipping, epsilon-filled data or silent row removal. Display rounding is separate from saved results.

| Output                    | Frozen v1 method and limitations                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Per concentration         | n, mean, median, min/max, sample SD with `ddof=1`, Q1, Q3, IQR, raw MAD and normal-scaled MAD. n=0 has no numeric statistics; n=1 has no sample SD.                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Quantiles                 | NumPy `quantile(method="linear")`, matching the existing interpolation convention.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| IQR flags                 | Within each approved concentration group, values strictly outside Q1−1.5×IQR or Q3+1.5×IQR. With fewer than four observations or zero IQR, return the flag rule as unavailable; still report defined descriptive statistics. No automatic exclusion.                                                                                                                                                                                                                                                                                                                    |
| MAD                       | Raw median absolute deviation and SciPy normal-scaled MAD, with the scaling named. Zero MAD is reported as zero dispersion; no division by it or synthetic epsilon score. v1 adds no unsupported MAD-based exclusion threshold.                                                                                                                                                                                                                                                                                                                                         |
| Mean confidence interval  | Within each concentration, percentile bootstrap, 95%, 10,000 resamples and a fixed batch size of 256. Resample complete records within that group; take the 0.025 and 0.975 quantiles of the resampled means using `method="linear"`. n<2 or a degenerate empirical distribution returns CI unavailable with its reason. No silent switch to SciPy's default interval method.                                                                                                                                                                                           |
| Quadratic                 | Fit the available concentration means with equal weight: y=a×x²+b×x+c, including an intercept. Center/scale x and numerically scale y, check full rank/singular values, then express coefficients in the original concentration units. Use statsmodels OLS and explicitly record equal weighting; do not substitute all rows or precision weights.                                                                                                                                                                                                                      |
| Fit availability          | At least three distinct concentration means are necessary for the three coefficients. Three groups may show a saturated descriptive curve, but training R² is labeled saturated, validation and candidate output are unavailable. Four groups are required for v1 LOOCV and candidate screening.                                                                                                                                                                                                                                                                        |
| Training metrics          | Training R²=1−SSE/SST on the group means, with intercept; constant response makes R² unavailable. Training RMSE=√mean(error²), not √`mse_resid`. Report the number of fitted groups and residual degrees of freedom.                                                                                                                                                                                                                                                                                                                                                    |
| LOOCV                     | With all four tested concentrations, hold out one concentration mean, refit on the other three, predict the held-out mean, and aggregate the four out-of-fold errors into RMSE. This is leave-one-observed-concentration-out on group means, not row-level CV. Show each held-out prediction in original yield units before computing aggregate RMSE with a common scale. Mark the 0 and 4 folds as extrapolation beyond their training range. Do not fit preprocessing using its held-out outcome.                                                                     |
| Best tested condition     | The tested concentration(s) with the highest approved sample mean yield. Means, ranking and ties use the same exact rational means of the sealed decimal yields: [0.10, 0.20] and [0.15, 0.15] remain tied and do not create spurious regression variation. Show group n and CI availability; this is a descriptive comparison, not a significance or global-optimum claim.                                                                                                                                                                                             |
| Model-estimated candidate | Consider an interior vertex only when the full fit has numerical rank, acceptable conditioning, concavity beyond floating-point roundoff and a vertex strictly inside the observed 0–4 range. Require all four leave-one-concentration refits also to retain concavity and interior vertices within that same full observed range. Otherwise suppress the candidate and state which check failed. Show the leave-one-out vertex range as sensitivity, not a confidence interval. Passing these structural checks does not establish a scientifically validated optimum. |

The proposed v1 numerical policy uses `eps = np.finfo(np.float64).eps`, an SVD rank cutoff `max(rows, columns) × eps × largest_singular_value`, and conditioning acceptable only when `condition_number × eps <= sqrt(eps)`. On each training set, center x at its mean and scale by its maximum centered absolute value; In beta.19, centre the exact group means and scale their deviations before float64 fitting; use the original maximum absolute response scale for the conservative concavity check, with one only for an all-zero response. Coefficients, predictions and metrics derive from the same centred fit; see the current protocol. For the scaled coefficient vector, require the quadratic coefficient to be below `−64 × eps × condition_number × max(1, max(abs(coefficients)))` before declaring numerical concavity. This is a conservative engineering margin proposed for review, not a statistical significance threshold or a proof of coefficient stability. Freeze it with flat/nearly-flat fixtures before the algorithm version is released. Do not use a scientific minimum mass threshold or invent a response range to make a fit pass. If any fold loses rank or produces non-finite output, mark LOOCV and the candidate unavailable; do not average only successful folds. Convex curves, boundary/exterior vertices and missing concentrations do not produce an interior candidate. Do not clamp negative model predictions to zero.

The implemented quantile and robust-scale definitions come from [NumPy quantile](https://numpy.org/doc/stable/reference/generated/numpy.quantile.html), [SciPy IQR](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.iqr.html), and [SciPy MAD](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.median_abs_deviation.html). Bootstrap options and warnings are described by [SciPy bootstrap](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html). These are method definitions, not evidence that a small classroom sample supports accurate confidence coverage.

OLS requires an explicit intercept; rank and an empty least-squares residual array need deliberate handling. Four means and three fitted parameters leave only one training residual degree of freedom; a three-mean training fold leaves zero. This follows from the model dimensions and makes a high training R² particularly weak evidence here. See [statsmodels OLS](https://www.statsmodels.org/stable/generated/statsmodels.regression.linear_model.OLS.html), [R²](https://www.statsmodels.org/stable/generated/statsmodels.regression.linear_model.OLSResults.rsquared.html), [RMSE](https://www.statsmodels.org/stable/generated/statsmodels.tools.eval_measures.rmse.html), and [NumPy least squares](https://numpy.org/doc/stable/reference/generated/numpy.linalg.lstsq.html).

## Independence and reproducibility

The present schema does not establish that every row is an independent experimental replicate. Student ID, group name, upload count and image count do not prove independence. Record `resampling_unit="record_assumed_independent"` and display that assumption. Multiple measurements of one experiment must not be marketed as extra independent experiments. If independence cannot be supported, the bootstrap remains an explicitly exploratory calculation; the report states that its CI may be misleading. Cluster/hierarchical resampling requires an independently defined experimental-unit identifier and is deferred.

Use an explicit PCG64 generator. Store the 128-bit seed as 32 lowercase hexadecimal characters so JavaScript cannot lose integer precision; Python converts it exactly. The default is the first 16 SHA-256 digest bytes of the JCS preimage `{schema: "echoclass.scientific-seed.v1", dataset_hash, settings_without_seed}`. An explicit user seed, if exposed later, must satisfy the same format. Create `SeedSequence(int(seed_hex, 16)).spawn(4)` once and assign `Generator(PCG64(child))` streams to concentrations in the order 0,1,3,4, including missing groups so the other groups' streams do not shift.

Save the algorithm version, code commit/source digest, Python and library versions, numerical backend/platform fingerprint, generator, seed, quantile/SD/bootstrap methods, resample count/batch size and the complete selection policy. Same seed alone does not guarantee cross-version or cross-machine identity. The same locked environment must reproduce the scientific-result hash; a different environment produces a separately labeled numerical comparison, not a false exact match. The proposed comparison uses `abs(new-old) <= 1e-12 + 1e-10 × abs(old)` for each finite saved numeric output, with exact agreement required for IDs, counts, selection, availability reasons and candidate/flag decisions. Report every mismatch; this tolerance is an interoperability diagnostic, not a scientific equivalence claim. [NumPy random compatibility](https://numpy.org/doc/stable/reference/random/compatibility.html), [NumPy SeedSequence](https://numpy.org/doc/stable/reference/random/parallel.html)

## Execution, failure and startup recovery

The application deployment remains one Node dispatcher and one local FastAPI worker. Use the existing SQLite pending runs as the queue, ordered by creation time then ID, and dispatch registered scientific runs only. A second dispatcher is unsupported and must not silently claim an already running task. Claim with `WHERE status='pending'`, not the general same-state-capable update method. Persist attempt number and an unpredictable attempt token before starting network work. Terminal completion compares that attempt token so a late response cannot finish a different attempt.

Proposed initial operational limits are explicit product limits to test, not performance claims: 500 candidate records, 8 MiB internal request bytes, 2 MiB result bytes, ten pending scientific runs per database, ten create/reproduce requests per actor per minute, one actual Python calculation at a time, and two total execution attempts per run. Request replay does not consume queue capacity. Refuse excess work before sealing or accepting an internal body; do not silently truncate a cohort or result.

FastAPI exposes one bounded raw analysis endpoint and a health/version endpoint, binds loopback only, uses one Uvicorn worker and accepts only the configured Node-to-worker credential. It invokes the same pure `analyze()` function used by pytest and reproduction. No business identity or database authority is delegated to this credential. Do not add CORS or expose internal interactive docs in the deployed application.

The worker owns one real concurrent Future and keeps its one-calculation slot until that Future actually completes; HTTP cancellation alone must not release it while a thread continues computing. An operation has a 30-second cooperative wall-clock budget measured by a monotonic clock, with checks between bounded bootstrap batches and CV folds; Node's response deadline is 35 seconds. Generate the fixed bootstrap batches with NumPy and collect their mean statistics, then apply the declared percentile method; compare the numerical method with a controlled SciPy reference fixture. Passing `batch=256` to one long SciPy call does not itself provide an application cancellation callback. No unbounded work is admitted while an earlier timed-out calculation remains active. If a calculation does not stop, report worker unavailable and require a controlled worker restart rather than accumulating background calculations. Test the real behavior; an asynchronous route is not evidence that CPU work is isolated or canceled. [FastAPI execution model](https://fastapi.tiangolo.com/async/)

| Event                                                                        | Durable run behavior                                                                                                                                                                                                                                                             |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Created and sealed                                                           | pending, with empty execution result                                                                                                                                                                                                                                             |
| First atomic claim                                                           | running, attempt 1 persisted                                                                                                                                                                                                                                                     |
| Transient connection failure, worker busy/unavailable or interrupted process | At most one retry with the same sealed bytes, configuration and seed after a five-second backoff and readiness check; persist the failure summary and attempt 2 before dispatch; keep run running. If readiness is still absent, finish failed rather than polling indefinitely. |
| Hash/schema mismatch, invalid worker output or contradictory provenance      | failed immediately; no retry that could hide a deterministic integrity error                                                                                                                                                                                                     |
| Valid report, including unavailable scientific metrics                       | completed with one checked result envelope                                                                                                                                                                                                                                       |
| Second attempt fails                                                         | failed with the bounded attempt history and safe error code                                                                                                                                                                                                                      |
| Late/repeated response after terminal commit                                 | No mutation; compare saved outcome for idempotent acknowledgement                                                                                                                                                                                                                |

A timeout can have an unknown computational outcome, but Python is stateless and has not written results; Node alone decides the durable terminal outcome. Never mark completed from an exit code/HTTP 200 without validating result schema, finite numbers, expected input/configuration fingerprints and environment.

On Node startup, dispatch pending registered runs after worker/version checks. Treat a previously running attempt as interrupted, retain its summary, and use the remaining attempt if available; otherwise finalize failed. Never return running to pending or failed to running. The supported startup procedure establishes a single dispatcher and quiescent/restarted worker before recovery, so it does not overlap an old in-flight calculation. Invalid sealed inputs remain blocked with a reported integrity problem; do not rewrite old snapshots or relax the SQL completeness guard to force a terminal transition.

Recheck the requesting account's active role and current class/record scope before dispatch and before accepting a result; background work uses the durable requester identity, not a stored browser session secret. Changed authority stops the run with a safe authorization-change failure. Normal result reads use the caller's fresh session, including a final synchronous authorization check after asynchronous work and before sending report bytes.

A terminal failed run is immutable. The UI can offer “重新分析当前数据”, which creates a new request/token and selects current records. It must not call that an exact retry of an old dataset. Read-only reproduction is available only for a completed registered run with a comparable baseline and uses that run's saved snapshots and configuration; it creates no new run/input, changes no result and cannot borrow the current review or live record values. Production execution requires the frozen environment identity. Only the read-only reproduction path may explicitly request a different-environment comparison; that response can never enter `finishScientificRun`. Persistent historical rerun lineage is outside this milestone.

The result schema is `echoclass.scientific-result.v1`. It contains input/configuration fingerprints, policy, candidate/included/excluded IDs and reasons, per-group descriptive outputs and CI availability, IQR flags, regression coefficients/diagnostics, four fold predictions and aggregate LOOCV, best-tested condition(s), optional candidate with its checks, and limitations. Operational metadata separately contains run/attempt IDs, timestamps, versions and failure summaries. Never include Python traceback, environment secrets or arbitrary rendered HTML in the public result.

The report should answer five plain-language questions: which records were used; what each tested concentration showed; what was unusual; how well the exploratory curve predicted held-out concentrations; and what to test next. Show “实测中平均得率最高” separately from “模型提示的待验证浓度”. Display missing-data and independence limitations beside the affected result. Put hashes/seed/version in a compact reproducibility detail section, not the main user flow. Retain the existing legacy report with its current exploratory label rather than silently replacing it.

One anonymous synthetic demo should exercise the same pure Python code with a named fixed seed and obvious `synthetic_demo` labeling. It does not create classroom records/reviews, claim real observation provenance or manufacture user/effectiveness counts. A small offline example report and the corresponding synthetic fixture are enough; no dashboard redesign or conversational AI is needed.

## Bounded implementation and acceptance

Implement in three reviewable steps, after the predecessor gate:

1. Freeze schemas/JCS vectors and the forward registration/state guards; implement atomic production sealing and the narrow repository. Prove current-row/review selection and idempotent replay before adding algorithms.
2. Implement and test the pure Python pipeline plus thin FastAPI transport; connect the single dispatcher, finite retry/startup recovery and terminal persistence.
3. Add the small real report and synthetic demo, read-only reproduction, reproducibility documentation and final integrated gates.

Required tests are finite and tied to these risks:

- Cross-language canonical byte/hash golden vectors and deliberate one-field/one-byte/review/order mutations; invalid-number and JSON-type rejection.
- Hand-calculable descriptive and regression fixtures; known parabola, constant/flat/convex data, missing concentration, saturated three-group fit, zero SD/IQR/MAD, small/degenerate bootstrap groups, rank failure and representational overflow. Verify the four held-out predictions and aggregate RMSE independently of the production helper.
- Same locked input/config/seed/environment yields the same scientific-result hash; reordered incoming records canonicalize to the same sorted cohort; changed review or measurement changes the corresponding digest. Demonstrate that a different environment is not called exact reproduction.
